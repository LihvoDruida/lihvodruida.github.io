# Site 4.3.1 — діагностика й виправлення відкату деплою

Повний пакет поверх Site 4.3.0. Потрібен запущений Dashboard 3.13.0 або новіший із capability `guild:raid-history:v2`. Дашборд у цьому hotfix не змінювався.

## Що відомо з наданого логу

Образ Site 4.3.0 успішно зібрано, типи й тести всередині Docker пройшли, контейнер запущено. До повідомлення про перевірку публічних маршрутів виконання не дійшло. Старий скрипт між запуском і цим повідомленням чекає healthy та виконує локальний `/site-api/v1/status`. При невдалому readiness він мовчки повертав код 1 і запускав відкат, приховуючи причину.

Найімовірніше джерело збою — readiness зв’язку з дашбордом. **За самим логом не доведено**, чи це старий запущений Dashboard, різні bridge token, проблема Docker-мережі або недоступна PostgreSQL. Успішний Docker build не перевіряє живий сервіс дашборда. Site 4.3.0 потребує нової capability з Dashboard 3.13.0; розпаковані файли без перезбірки та перезапуску дашборда її не додають у чинний контейнер.

## Що виправлено

1. Після збирання нового образу перевіряється фактичний приватний `/api/site/status` дашборда: HTTP-доступ, протокол, сховище й обов’язкові capabilities. Це відбувається **до заміни чинного контейнера сайту**. Несумісна пара зупиняє встановлення з конкретним поясненням.
2. Перевірка використовує короткий одноразовий контейнер із новим образом і його налаштуваннями, `--no-deps`, `--pull never`, `--rm`. Залежні сервіси не запускаються, сервісні порти не публікуються; `--use-aliases` не вмикається. CLI-параметри звірено з [офіційною документацією Docker Compose](https://docs.docker.com/reference/cli/docker/compose/run/).
3. Локальний readiness після запуску показує безпечний код помилки й додатково перевіряє upstream. При наступній помилці виводиться етап: start, healthcheck, local-integration або public-routes. Відкат збережено для збоїв після заміни контейнера.
4. Додано `make integration-check`: вона передає актуальний діагностичний скрипт у вже запущений контейнер сайту через stdin. Команда працює й після відкату на попередній образ, не потребує збірки або перезапуску сайту. Вона використовує фактичне оточення чинного контейнера.
5. Діагностика розрізняє відсутню capability, несумісний протокол, відхилений доступ, DNS, відмову з’єднання, timeout та HTTP-помилки. Токени, заголовки авторизації, необроблені відповіді й внутрішні мережеві повідомлення до логу не виводяться.

## Швидка перевірка на VPS

Завантажити повний архів Site 4.3.1 у `/tmp`. Поточні `.env` до архіву не входять і при розпакуванні зберігаються.

```bash
unzip -t /tmp/lihvodruida-site-v4.3.1-deploy-readiness.zip
unzip -o /tmp/lihvodruida-site-v4.3.1-deploy-readiness.zip -d /srv
cd /srv/lihvodruida-site
make integration-check
```

Команда читає стан дашборда через поточний контейнер сайту. Якщо контейнер сайту зупинений, потрібен його запуск або звичайний `make up`: автоматична перевірка з нового образу відбудеться до заміни контейнера.

| Результат | Дія |
|---|---|
| `PASS dashboard protocol, PostgreSQL and required capabilities` | Виконати `make up` для Site 4.3.1 |
| `dashboard_capabilities_missing: guild:raid-history:v2` | Встановити й перезібрати Dashboard 3.13.0; повторити перевірку |
| `dashboard_protocol_incompatible` | Перевірити фактичний запущений дашборд і версію протоколу |
| `bridge_access_rejected` | Перевірити однаковий `PUBLIC_SITE_BRIDGE_TOKEN` в обох запущених контейнерах та внутрішній маршрут; ключі не публікувати |
| `dashboard_dns` | Перевірити підключення обох сервісів до `mistblossom_edge` і ім’я `dashboard` |
| `dashboard_connection_refused` | Перевірити, що контейнер dashboard запущений і приймає HTTP на 3000 |
| `dashboard_http`, HTTP 503 | Перевірити стан Dashboard і доступність PostgreSQL / схеми БД |
| `integration_non_json` або `legacy_dashboard_route` | Перевірити приватну адресу `http://dashboard:3000`, маршрутизацію й фактичну відповідь сервісу |

Відхилений HTTP 403 сам по собі не доводить різний токен: його також може спричинити маршрут або перевірка походження. Діагностика навмисно не приписує йому єдину причину.

## Якщо ще не запущено Dashboard 3.13.0

Зберегти резервну копію БД та чинної конфігурації. Завантажити раніше наданий повний архів дашборда у `/tmp`.

```bash
cd /srv/mistblossom
make backup
unzip -t /tmp/lihvodruida-dashboard-v3.13.0-raid-history.zip
unzip -o /tmp/lihvodruida-dashboard-v3.13.0-raid-history.zip -d /srv
python3 /srv/mistblossom/deploy/prepare-unified-env.py --site-dir /srv/lihvodruida-site
cd /srv/mistblossom
make rebuild-dashboard
docker compose -p mistblossom up -d --no-deps --no-build --wait --wait-timeout 90 dashboard
docker compose -p mistblossom up -d --no-deps --no-build --pull never --force-recreate cron
make internal-check
cd /srv/lihvodruida-site
make integration-check && make up
```

Якщо `prepare-unified-env.py` змінив `.env` сайту, чинний контейнер сайту ще може мати попереднє оточення. Автоматична перевірка під час `make up` використовує вже актуальні налаштування нового образу. Розбіжність оточення старого й нового контейнерів треба врахувати при інтерпретації результату `make integration-check`.

Після успіху: `make status`, публічний `/site-api/v1/status` має повернути `integration: ready`; `make up` також сам перевіряє публічні sync, guild та applications. Початкове наповнення історії сезонів іде плановим cron. Попередня інструкція функціональної синхронізації — `RAID_HISTORY_SYNC_2026-10-16_UA.md`.

## Виконані перевірки

- Повний `build:ci` Site 4.3.1: типи, тести, контент, deploy-перевірки, production build і standalone — успішно.
- 41 Node-тест, включно з парною передачею даних дашборда, CMS/SQL і шістьма новими перевірками діагностики: 41/41, без пропусків.
- Оркестрація деплою з контрольованим Docker CLI: 19/19. Перевірено відмову preflight без заміни сайту, порядок build → preflight → up, читання через чинний контейнер та відкат після пізнього збою.
- Production standalone: 8/8. Скопійований у runtime діагностичний скрипт запущено проти контрольованого HTTP-upstream: сумісний дашборд прийнято, відсутня capability пояснена; токен у вивід не потрапив.
- ZIP перевіряється на центральний каталог, CRC, SHA-256 архіву та кожного файла до й після збереження.

Контрольований Docker CLI не замінює реальний Docker daemon. Збірку Docker, мережу VPS та фактичний readiness живого дашборда в цьому сеансі не перевірено; доступу до SSH немає. Справжню причину саме цього відкату встановить нова діагностика на VPS. Живі заявки, матеріали й Discord-повідомлення не створювалися.
