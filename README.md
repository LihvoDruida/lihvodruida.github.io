# Лігво Друїда · 4.0.1

Український публічний сайт на **Node.js 24, Next.js 16.3.5, React 19.2.8 і TypeScript**. Це повний перехід із Jekyll на серверний застосунок, сумісний із чинним дашбордом Mistblossom.

## Запуск

```bash
cp .env.example .env
npm ci
npm run build:ci
npm start
```

Для розробки: `npm run dev`. Production standalone включає public, статичні чанки та контент. Запуск `npm start` не потребує початкового дерева node_modules після збірки. Використовуйте Node 24.

### На VPS поряд із дашбордом

Дашборд: `/srv/mistblossom`. Новий сайт: `/srv/lihvodruida-site`.

```bash
cd /srv/lihvodruida-site
make check
make deploy
```

Або без make: `bash deploy/deploy.sh`. Скрипт створить відсутній `.env`, використає чинну мережу `mistblossom_edge`, перевірить конфігурацію, збере тільки сайт і дочекається healthy. При невдалому запуску спробує повернути попередній здоровий образ. Наявний `.env` зберігається. `make logs`, `make status`, `make restart`, `make stop` керують лише сайтом. Потрібні Bash, Docker Compose, Python 3 та flock; Node.js на хості не потрібен.

**Повна інструкція:** [deploy/VPS.md](deploy/VPS.md). Одноразове підключення DNS/Nginx/TLS описане там окремо. Нова конфігурація Nginx використовує Docker alias сайту; приклад з localhost для контейнерного Nginx виправлено. Порт `127.0.0.1:3001` лишається для перевірок із хоста.

**GitHub Pages не запускає Node.js.** Старий workflow публікації Jekyll перенесений до `legacy/jekyll`, новий CI перевіряє Next.js без автоматичного розгортання. Після зміни гайдів або новин в дашборді **не потрібен** деплой публічного сайту: контент читається із PostgreSQL через API. Оновлення коду або статичних ресурсів потребують нового деплою. Автоматичне керування вашим VPS у цей архів не включене.

## Система обміну

Дашборд залишається джерелом істини. Нової бази заявок, Discord-бота чи OAuth-дублікатів тут немає. Сайту не потрібні токени Discord, PostgreSQL, GitHub або адміністратора.

| Дані | Напрямок | Поведінка |
| --- | --- | --- |
| Нова заявка | Браузер → `DASHBOARD_URL/api/site/applications` POST | Чинна валідація, захист, створення запису та Discord-сповіщення дашборда |
| Статус, рішення офіцерів | Дашборд → Node-сайт → браузер | Автооновлення 30 с, пошук за персонажем/номером, фільтри класу та статусу |
| Склад, рейтинг, прогрес, сезони | Дашборд → Node-сайт → браузер | Оновлення 120 с, об’єднання паралельних запитів і кеш 60 с |
| Опублікований розклад рейдів | Той самий публічний snapshot гільдії | Лише події, які експортує чинний dashboard API; час за Києвом |
| Професії | `_data/professions.yml` | Окремий архівний довідник із явною позначкою; чинний live API професії не експортує |
| Адони, авторські персонажі | CurseForge API + архів `_data/my_mods.yml`, `_data/characters.yml` | Адони автоматично оновлюються через серверний API ключ; YAML застосовується лише як fallback |

### Чому POST безпосередньо до дашборда

Чинний API сам застосовує перевірку Origin, країни, IP-ліміти, honeypot, правила полів, пошук недавніх дублікатів і Discord-повідомлення. Прямий HTTPS-запит з `credentials: omit` зберігає реальну IP-адресу користувача та ці механізми. Простий серверний proxy зводив би всіх заявників до IP сайту. Серверні GET не передають користувацькі cookies чи Authorization. Довільну адресу upstream через query передати неможливо.

У `.env` **дашборда** має залишитися:

```dotenv
PUBLIC_SITE_ORIGINS=https://lihvodruida.pp.ua,https://www.lihvodruida.pp.ua
```

Для іншого або локального домену додайте точний origin у цю змінну на тестовому дашборді та перезапустіть його. Не вимикайте перевірку Origin. `DASHBOARD_URL` сайту — HTTPS origin без шляху; у dev дозволені localhost/127.0.0.1 через HTTP. Production HTTP до upstream не допускається.

Після тайм-ауту POST сайт **не повторює запис автоматично**: відповідь могла загубитися після збереження. Він пропонує перевірити статус за персонажем. Чинна серверна перевірка недавніх дублікатів додатково залишається активною. Номер відстеження показується лише у відповіді власнику заявки; у публічний список він не копіюється.

### Свіжість, помилки й навантаження

- GET `/api/bridge/guild` та `/api/bridge/applications` — локальні публічні маршрути читання. Формат `{data, sync}` містить source, stale, checkedAt, updatedAt.
- Одна активна upstream-операція на ключ у межах процесу; обмежена кількість ключів пошуку. Для заявок кеш 15 с. Невдалі запити мають експоненційний cooldown до 60 с.
- ETag не змінюється від самого generated_at/updated_at тіку. Незмінений payload повертає 304; зміна статусу, складу або прогресу змінює ревізію.
- Браузер зупиняє запити у прихованій або офлайн-вкладці, скасовує їх при виході, не допускає накладання і застосовує backoff із jitter. Пошук заявок має затримку 350 мс.
- Upstream timeout 8 с, браузерний GET timeout 10 с, POST timeout 20 с. Тіло upstream обмежено 4 MiB фактично прочитаних байтів, перенаправлення заборонені.
- Після збою кеш гільдії доступний до 24 годин з позначкою «застарілі дані», заявок — до 2 хв. Потім гільдія використовує датований YAML-архів; список заявок повертає 503, а не удавану порожню успішну відповідь.
- Кеш працює в пам’яті одного Node-процесу; між кількома репліками він не спільний. Для невеликого сайту використовуйте одну репліку; чинний API дашборда має власні ліміти.

## Контент та сумісність

Збережені всі **7 гайдів, 8 адонів, 2 спільноти**, авторські персонажі, дані гільдії, сезони, професії, зображення й умови підтримки. В архіві немає новин: сторінка чесно показує порожній стан; `_news/*.md` підтримуються для наступних публікацій.

Редактор дашборда працює з єдиним джерелом у PostgreSQL (`siteArticles`): створення, редагування й видалення одразу зберігаються у БД та через `GET /api/site/content` стають доступними на сайті (кеш до 60 с). Обкладинки зберігаються в `site_content_media`. Старі `_guides` / `_news` є тільки матеріалами одноразового імпорту й не читаються сторінками. HTML рендериться через React Markdown; скрипти Markdown не виконуються.

Оригінальні Jekyll-шаблони й кореневі сторінки лежать у `legacy/jekyll`; вони не є активними сторінками. Кореневі `_data`, `_guides` та `assets` лишаються робочими джерелами. Оригінальні Python-оновлювачі збережені, workflow update-data лишився ручним, як у вихідному архіві. Для його запуску потрібна гілка live та відповідні secrets репозиторію, як раніше.

Маршрути `/`, `/guild`, `/guild/apply`, `/guild/applications`, `/guides`, `/guides/:slug`, `/news`, `/news/:slug`, `/mods`, `/donate`, `/feed.xml`, `/robots.txt`, `/sitemap.xml` підтримуються. Варіанти з кінцевим `/` обробляє Next.js; старі основні `.html` адреси мають redirects. Старий OAuth callback веде до форми вступу. Авторизація лишається окремою системою дашборда.

## Дизайн і продуктивність

Повністю нова адаптивна оболонка: лісова ілюстрація з вашого архіву, контрастні зелені акценти, редакційні картки гайдів, мобільне меню, форма з двома зрозумілими секціями, склад із пошуком/ролями/рейтингом та пагінацією по 24 персонажі. Гайди, новини та RSS рендеряться динамічно з read-only API дашборда; runtime потрібний для їх оновлень без перебілду. Hero завантажується пріоритетно через Next Image; решта зображень — ліниво. Зоряний canvas відновлено з архіву з дотриманням prefers-reduced-motion; використовується повернена тепла палітра. Збережена підтримка reduced motion, клавіатури, focus, skip link, native select і підписів полів.

## Діагностика

`docker compose logs -f site` — структуровані JSON-події `bridge.refreshed`, `bridge.failed` з resource, requestId та durationMs. Запити пошуку, Discord, BattleTag, тексти заявок і токени в логи не потрапляють. Незмінені тики приховані; `SITE_DEBUG_LOGS=true` вмикає `bridge.unchanged` на рівні debug. Здоров’я Node-процесу: `/api/health`; стан джерела даних дивіться через sync у `/api/bridge/guild`. Healthcheck не заявляє доступність PostgreSQL/Discord.

## Перевірки

```bash
npm run typecheck
npm test
npm run check:content
npm run build
```

Тести перевіряють об’єднання запитів, bounded stale/cooldown, помилки контрактів і oversized payload, відсутність приватних полів, query allowlist, ETag/304, форму Horde/BattleTag і збереження контенту. Після запуску потрібне приймання з вашим живим дашбордом: створення однієї тестової заявки, Discord-сповіщення, зміна статусу офіцером і поява цього рішення на сайті. Ці дії навмисно не виконуються локальними автоматичними тестами.

За наявності Playwright та Chromium додатково доступний `node scripts/check-browser.cjs`. Він сам запускає standalone на localhost:3217 і перехоплює всі API-запити, включно з POST; живих заявок не створює. Можна вказати `SITE_QA_PLAYWRIGHT` (модуль) та `SITE_QA_CHROMIUM` (шлях до браузера), `SITE_QA_OUTPUT` (каталог звіту). Скриншоти за замовчуванням не зберігаються; для локального візуального огляду встановіть `SITE_QA_SCREENSHOTS=1`.

### Внутрішній SSR-міст (для уникнення Cloudflare 403/DNS loop)

Public site і dashboard уже спільно використовують `mistblossom_edge`. У **обох** `.env` задайте однаковий `PUBLIC_SITE_BRIDGE_TOKEN` (`openssl rand -hex 32`), у `.env` сайту залиште `DASHBOARD_INTERNAL_URL=http://dashboard:3000`. Кореневий `docker-compose.yml` дашборда передає токен контейнеру. Це **окремий** секрет лише для GET/HEAD `api/site/*`, не `INTERNAL_API_TOKEN`; не додавати його в `NEXT_PUBLIC_*`. Публічна форма заявок продовжує надсилати POST через публічний HTTPS origin з перевіркою Origin. Без токена SSR користується старим публічним HTTPS URL.
